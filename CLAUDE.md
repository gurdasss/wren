# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Wren is a small, class-based, fiber-concurrent scripting language meant to be embedded in host applications. This repo holds the VM only (the standalone CLI/REPL is a separate project, wren-cli). The VM has no dependencies and has to compile cleanly as both C99 and C++98, so don't use C11 features or C/C++-incompatible constructs (for example, implicit `void*` casts are not allowed in C++).

## Build

Build files are generated by premake (`projects/premake/premake5.lua`, regenerated with `python3 util/generate_projects.py`). Don't hand-edit the files in `projects/make*`, `vs20xx` or `xcode`. Edit the premake script and regenerate.

```sh
make -C projects/make                          # default config=release_64bit
make -C projects/make config=debug_64bit       # debug build → bin/wren_test_d
make -C projects/make help                     # lists configs and targets
```

- Use `projects/make.mac` on macOS and `projects/make.bsd` on BSD.
- Configs: `{release,debug}_{64bit,32bit,64bit-no-nan-tagging}`.
- Targets: `wren` (static lib → `lib/`), `wren_shared`, `wren_test` (test runner → `bin/wren_test`, or `bin/wren_test_d` for debug builds).
- To build a single-file amalgamation, run `python3 util/generate_amalgamation.py > wren.c`.

## Tests

```sh
python3 util/test.py                 # run everything against bin/wren_test
python3 util/test.py --suffix=_d     # run against the debug binary bin/wren_test_d
python3 util/test.py language/closure   # subset: prefix match on path relative to test/
```

To run one script directly, use `bin/wren_test test/core/list/add.wren`. Paths must start with `test/`, because API tests are recognized by the `test/api` and `test/benchmark` prefixes.

CI (`.travis.sh`, run by `.github/workflows/.githubCI.yml`) builds and tests all four 64-bit configs: debug and release, with and without NaN tagging. Changes to value representation should pass both the NaN-tagging and no-NaN-tagging builds.

### Test format

Tests are `.wren` scripts annotated with comments that `util/test.py` parses:
- `// expect: <output>`: an expected stdout line, matched in order
- `// expect error` / `// expect error line N`: a compile error on this line or on line N
- `// expect runtime error: <msg>` (or `expect handled runtime error:`)
- `// stdin: <text>`, `// skip: <reason>`, `// nontest` (a helper module, not run directly)

Suites: `test/language` covers the compiler and VM semantics, `test/core` covers built-in classes, and `test/limit` covers hardcoded VM limits. `test/meta` and `test/random` cover the optional modules, `test/regression` holds bug repros, and `test/benchmark` holds perf scripts (run them with `util/benchmark.py`). `example/` scripts also run as tests.

**API tests** (`test/api/`) test the C embedding API. Each one is a `foo.wren` + `foo.c`/`foo.h` pair. To add one, write the `.c` file's bind function and register it in `test/api/api_tests.c`, where `APITest_bindForeignMethod`/`APITest_bindForeignClass` dispatch by test name. For tests that drive the VM from C after the script runs, add a hook in `APITest_Run`. Premake picks up `test/api/*.c` with a glob, but the generated Makefiles list every file explicitly. Regenerate the projects so the new file gets compiled.

## Architecture (src/)

- `include/wren.h` is the entire public embedding API: `WrenConfiguration` callbacks, slots, handles and foreign classes/methods. `wren.hpp` is a C++ wrapper include.
- `vm/wren_compiler.c` is a single-pass compiler. It goes straight from tokens to bytecode with no AST. Opcodes are defined via X-macros in `wren_opcodes.h`.
- `vm/wren_vm.c` contains the interpreter loop (`runInterpreter`, which uses computed goto when `WREN_COMPUTED_GOTO` is set), method dispatch, fibers, module loading/import resolution and the GC entry point.
- `vm/wren_value.c/.h` define the object model and GC'd heap types (ObjClass, ObjFiber, ObjClosure, ObjMap, etc.). `Value` is either NaN-tagged (`WREN_NAN_TAGGING`, the default) or a tagged union. Code must go through the `IS_*`/`AS_*`/`*_VAL` macros rather than assume a representation.
- `vm/wren_core.c` holds the built-in classes. Methods implemented in C are `DEF_PRIMITIVE(...)` functions (helpers live in `wren_primitive.c/.h`), and they're bound in `wrenInitializeCore`. Methods implemented in Wren live in `wren_core.wren`.
- `optional/` holds the `meta` and `random` modules, which can be compiled out with `WREN_OPT_META` / `WREN_OPT_RANDOM`.
- `vm/wren_common.h` holds the feature flags and limits, plus the debug switches: `WREN_DEBUG_GC_STRESS`, `WREN_DEBUG_TRACE_GC`, `WREN_DEBUG_DUMP_COMPILED_CODE`, `WREN_DEBUG_TRACE_INSTRUCTIONS` and others.

### Generated `.wren.inc` files

Wren-source modules (`wren_core.wren`, `wren_opt_meta.wren`, `wren_opt_random.wren`) are compiled into the VM as C string literals stored in the matching `.wren.inc` files. The build does **not** regenerate these files. After editing a `.wren` module, regenerate its `.inc` and commit both:

```sh
python3 util/wren_to_c_string.py src/vm/wren_core.wren.inc src/vm/wren_core.wren
```

The arguments are output first, then input.

### GC caution

Any C code that allocates can trigger a collection. Temporarily root newly created objects with `wrenPushRoot`/`wrenPopRoot` while they aren't yet reachable from the stack or another object. Building with `WREN_DEBUG_GC_STRESS 1` surfaces missing roots.
